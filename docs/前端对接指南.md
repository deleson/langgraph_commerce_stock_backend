# 前端对接指南

本文面向 Android / Web 前端开发，说明如何接入当前后端 API。

## 一、基础地址

后端统一 API 前缀：

```text
/api/v1
```

本地开发常见地址：

```text
http://127.0.0.1:8000/api/v1
```

生产部署第一版通过 Nginx 暴露 HTTP 80 端口。实际公网 IP 或域名应以部署环境为准。

## 二、统一响应格式

成功响应外层结构：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

错误响应外层结构：

```json
{
  "code": 40001,
  "message": "error message",
  "details": [
    {
      "field": "email",
      "reason": "invalid email"
    }
  ]
}
```

前端处理建议：

| 字段 | 含义 | 前端处理 |
| ---- | ---- | -------- |
| `code` | 业务状态码，`0` 表示成功 | 非 0 时走错误提示 |
| `message` | 响应说明 | 可展示给用户或用于调试 |
| `data` | 真实业务数据 | 页面渲染使用 |
| `details` | 字段级错误列表 | 表单错误提示使用 |

## 三、登录和 Token

登录请求建议携带设备信息，Android App 至少应传 `platform=android` 和稳定的 `device_fingerprint`：

```json
{
  "email": "user@example.com",
  "password": "your-password",
  "platform": "android",
  "device_fingerprint": "client-generated-stable-id",
  "device_name": "Pixel 7",
  "app_version": "1.0.0"
}
```

登录成功后，后端返回：

```json
{
  "access_token": "...",
  "refresh_token": "...",
  "token_type": "bearer",
  "session_id": 123,
  "device_category": "mobile",
  "replaced_sessions_count": 1
}
```

`session_id` 是服务端登录会话 ID，前端通常不需要手动拼接到请求里，但可以用于调试日志。`device_category` 用于说明当前登录属于 `mobile`、`web` 还是 `unknown`。

同类设备登录规则：

```text
android / ios 属于 mobile；
web 属于 web；
同一账号同一时间只能保留一个 mobile 会话和一个 web 会话；
新手机登录会踢掉旧手机登录，但不会踢掉 Web 登录；
新 Web 登录会踢掉旧 Web 登录，但不会踢掉手机登录。
```

需要登录的接口请求头：

```http
Authorization: Bearer <access_token>
```

推荐 App 登录流程：

```mermaid
flowchart TD
    A["打开 App"] --> B["读取本地 access_token"]
    B --> C{"是否存在"}
    C -->|否| D["进入登录页"]
    C -->|是| E["请求 /users/me"]
    E --> F{"是否 401"}
    F -->|否| G["进入首页"]
    F -->|是| H{"是否为同类设备替换"}
    H -->|是| I["弹窗提示账号已在另一台同类设备登录"]
    I --> J["清空 token 并进入登录页"]
    H -->|否| K["调用 /auth/refresh"]
    K --> L{"刷新成功"}
    L -->|是| G
    L -->|否| J
```

401 处理建议：

| 错误原因 | 前端处理 |
| -------- | -------- |
| `token has been revoked` | 清空本地 token，跳转登录页 |
| `session has been revoked` | 判断 `details.reason`，如果是 `replaced_by_same_category_login`，弹窗提示后跳转登录页 |
| `replaced_by_same_category_login` | 提示“账号已在另一台同类设备登录”，清空 token 后跳转登录页 |
| `refresh token has expired` | 清空 token 后跳转登录页 |
| `refresh token has been revoked` | 清空 token 后跳转登录页 |

退出登录建议：

```text
1. 调用 POST /auth/logout；
2. 本地删除 access_token 和 refresh_token；
3. 跳转登录页。
```

## 四、常见 HTTP 状态处理

| 状态 | 常见原因 | 前端处理 |
| ---- | -------- | -------- |
| 200 / 201 | 请求成功 | 读取 `data` |
| 400 | 请求参数或业务规则错误 | 展示 `message` 和 `details` |
| 401 | token 缺失、过期、被注销、服务端 session 被撤销 | 先判断是否被同类设备登录替换；否则尝试刷新 token，刷新失败后重新登录 |
| 403 | 无权限 | 提示无权限 |
| 404 | 资源不存在或不属于当前用户 | 提示资源不存在 |
| 422 | Pydantic 参数校验失败 | 表单字段提示 |
| 500 | 服务端异常 | 提示稍后重试 |

### 股票搜索页建议数据流

`GET /api/v1/market/stocks/search` 已经由后端统一编排数据库查询和少量 Provider 精确兜底。

前端不需要在搜索无结果时自行调用 `/market-sync/symbols/{symbol}` 后再重新搜索。当前后端会：

```text
1. 优先查询 market_symbols；
2. 名称 / 关键词搜索只读取数据库股票池，不在用户请求中高频调用 Tushare；
3. 数据库命中但名称为空、名称等于代码或来源仍是 mock，并且搜索词是 6 位 A 股代码时，才尝试 Provider 精确刷新；
4. 数据库无结果且搜索词是 6 位 A 股代码时，才调用配置的精确查询 Provider 补齐基础信息；
5. Provider 返回的基础信息会先写入 market_symbol_sources，再按 Provider 优先级刷新 market_symbols；
6. 返回统一搜索结果给前端，结果包含 symbol、name、market、exchange、currency、source。
```

```mermaid
flowchart TD
    A["用户输入股票代码或名称"] --> B["GET /market/stocks/search"]
    B --> C["后端查询数据库"]
    C -->|命中且基础信息可用| D["返回搜索结果"]
    C -->|名称/关键词未命中| E["返回空结果<br/>提示股票池可能未同步"]
    C -->|6 位 A 股代码缺失或占位| F["Provider 精确查询"]
    F --> G["写入 market_symbol_sources"]
    G --> H["按 Provider 优先级刷新 market_symbols"]
    H --> D
    D --> I["前端展示名称、代码、市场、交易所"]
```

股票基础信息池由后端通过 `POST /market-sync/symbol-pool` 或 Celery Beat 定时任务维护。Tushare 更适合低频股票池同步，BaoStock 更适合精确代码补齐和 K 线同步；前端不需要知道当前使用哪个 Provider。

股票详情页调用 `GET /api/v1/market/stocks/{symbol}/overview` 时，如果该股票基础信息已存在但 K 线尚未入库，后端会尝试按当前 Provider 同步所需 K 线后再返回详情。前端不需要自行调用 `/market-sync/stocks/{symbol}/candles`。


K 线刷新策略：

```text
1. 股票详情页和自选股展示优先读取后端数据库中的 K 线；
2. 如果 K 线不存在或超过服务端配置的过期天数，后端会按配置 Provider 尝试补齐；
3. 后端也可以通过 Celery Beat 定时提交 watchlist_candle_sync 任务，批量刷新自选股 K 线；
4. 前端不需要对每只股票主动调用 K 线同步接口，也不需要自己编排 Provider fallback；
5. 如果接口返回数据不足或风险提示，前端应展示“数据可能延迟/不足”的提示，不要展示为实时交易信号。
```

flowchart TD

## 八、回测页建议数据流

```mermaid
flowchart TD
    A["填写 symbol / market / start_date / end_date"] --> B["选择初始资金和风控参数"]
    B --> C["POST /backtests"]
    C --> D["展示 metrics"]
    D --> E["展示 daily_equity 曲线"]
    D --> F["展示 trades 列表"]
    D --> G["展示 warnings 和 disclaimer"]
```

重要说明：

```text
回测只基于历史 K 线和规则模拟；
历史表现不代表未来；
前端不要把回测结果展示为收益承诺。
```

单股回测响应成功状态是 `available`，不可用状态是 `unavailable`，前端不得使用通用任务状态 `success` 判断回测是否执行。单股回测请求不需要前端先调用行情同步接口。后端会优先使用数据库 K 线，并仅在数据缺失、数量不足或过期时尝试受控补齐；前端应根据 `status`、`unavailable_reason` 和 `warnings` 区分“回测成功”和“数据仍不可用”。

## 九、每日简报页模式开关数据流

前端进入每日简报页时，建议先读取日报模式状态：

```mermaid
flowchart TD
    A["进入每日简报页"] --> B["GET /daily-reports/mode"]
    B --> C["展示日报模式开关"]
    C --> D{"用户点击开关"}
    D -->|开启| E["PATCH /daily-reports/mode<br/>daily_report_enabled=true"]
    D -->|关闭| F["PATCH /daily-reports/mode<br/>daily_report_enabled=false"]
    E --> G["刷新开关状态和提示文案"]
    F --> G
    G --> H["GET /daily-reports/today"]
    H --> I["展示今日日报或手动生成入口"]
```

响应中的 `scheduler_enabled` 只表示服务端是否启用了全局 Celery Beat 日报调度。前端按钮只能控制当前用户的 `daily_report_enabled`，不能控制服务器定时器。

响应中的 `scheduled_time` 由服务端环境变量计算，格式为 `HH:mm`。前端应与 `timezone` 组合展示，例如“每日更新时间 18:00（Asia/Shanghai）”，不要在 Android 中写死时间。

如果 `effective_status` 为 `enabled_but_scheduler_off`，前端可以提示：

```text
日报模式已开启，但当前服务器未启用自动调度。你仍可以手动生成日报。
```

## 十、纸面交易页建议数据流

```mermaid
flowchart TD
    A["GET /paper-trading/accounts"] --> B{"是否有账户"}
    B -->|无| C["GET /watchlist 并勾选 1-50 只股票"]
    C --> C2["POST /paper-trading/accounts<br/>携带 watchlist_item_ids"]
    B -->|有| D["GET /paper-trading/accounts/{account_id}"]
    C2 --> D
    D --> E["展示账户、固定股票池、配置、持仓与区间绩效"]
    E --> F["用户手动执行 tick"]
    F --> G["POST /paper-trading/accounts/{account_id}/tick"]
    G --> H["刷新订单、成交、持仓、权益、运行记录"]
    D --> I["PATCH 账户名称 / 状态"]
    I --> J{"状态 closed？"}
    J -->|是| K["停止运行并展示最终绩效汇总"]
```

tick 响应中的 `items` 既包含已成交动作，也包含未成交股票及原因。前端不应把“订单数为 0”直接解释为任务失败，例如当前信号为 `sell` 但虚拟账户没有持仓时，后端会明确返回跳过原因。

账户详情的 `universe` 是创建时冻结的组合，前端应持续展示并明确“不会随自选股变化”。`performance` 是创建到当前或关闭时刻的区间汇总；`is_final=true` 时展示最终权益、累计盈亏、累计收益率、最大回撤、运行天数、成交数和未平仓数。

创建失败时，前端需要区分：空数组或超过 50 只由参数校验返回 `422`；包含非当前用户自选股 ID 返回 `400`。账户配置的 `max_symbols_per_tick` 不能小于固定股票池数量，否则返回 `400`。

纸面交易账户区分“关闭”和“删除”：关闭账户通过 `PATCH /paper-trading/accounts/{account_id}` 写入 `status=closed`，后端同时写入 `closed_at` 和最终权益快照，用于保留历史并冻结绩效；删除账户通过 `DELETE` 清理固定股票池、配置、持仓、订单、成交、权益和运行记录。两个操作都必须二次确认。

删除自选股时，前端应明确：只删除关注关系，不改变任何已创建纸面账户的固定股票池。以后新建账户时，该股票不再出现在可选列表中。

纸面交易必须展示：

```text
纸面交易仅用于研究和学习，不是真实交易，不构成投资建议，也不承诺未来收益。
```

## 十一、Android 客户端实现建议

| 能力 | 建议 |
| ---- | ---- |
| Token 存储 | 使用安全存储保存 `access_token` 和 `refresh_token` |
| 网络层 | 统一封装 base URL、Authorization Header、错误处理 |
| 401 处理 | 拦截 401 后自动 refresh，一次失败后跳登录 |
| 金额和比例 | 后端部分金额为 Decimal，前端按字符串或高精度类型处理更安全 |
| 时间字段 | 后端返回 ISO datetime，前端统一转本地时区展示 |
| 风险提示 | AI、策略、回测、纸面交易页面固定展示免责声明 |


### 日报通知补建

手动生成日报时，如果当日日报已经存在且请求 `notify=true`，后端会检查日报是否已经有关联通知；如果通知缺失或历史关联已失效，会补建 `daily_report` 通知，方便前端在通知中心展示今日简报入口。
